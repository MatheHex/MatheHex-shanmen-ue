## 1. 总体结论

**当前项目处于“底层框架和大量产品接入口已形成，准备统一 UI 契约与真实 UE 场景验收”的阶段，不是从零开始，也不是已完成可玩版本。**

已有比较可靠的基础包括：确定性身份、统一命中/防御结算、新物品事务及持久权威、资源预留与提交、存档故障恢复、Run 生命周期、动作互斥、剑法/御器/暗器/阵法/部分术法的执行与展示接口。物品“全入口唯一权威”仍在有限审计中，不由模块名或 ADR 声明自动成立。部分 HUD、投掷预览、御器外观、神识标记和物品详情已经存在，后续 UI 应复用它们背后的数据与命令接口。

仍不能等同于完成的部分包括：全套正式 UI、动画和特效实际播放、连续玩家输入体验、完整内容目录、数值平衡、长时性能、打包后端到端体验。尤其要避免把“命令成功分派”“回执被确认”“无头 World 测试通过”解释成“玩家已经在正式场景中看见并用好了该功能”。

## 2. 系统分层：六个模块与一条清晰边界

### 2.1 逻辑层级

下面是职责图，不是要求立刻重构成新的目录：

```text
玩家输入 / UI / 动画与特效
          │ 请求命令，读取投影
          ▼
产品组合层 demo_map
GameInstance 物品服务 + GameMode Run 根 + Controller/HUD + 各产品 Host
          │ 明确的领域调用
          ├── ShanmenItems：物品、资源事务、持久化
          ├── ShanmenCombatRuntime：动作、能力编排、各战斗体系
          └── ShanmenWorldGameplay：实体身份与 World 几何适配
                         │ 候选，不直接决定伤害
                         ▼
             ShanmenCombatCore：命中契约、纯结算、去重
                         │
                         ▼
                 ShanmenCore：基础身份与内容戳
```

### 2.2 实际模块职责

| 模块 | 已有职责/依赖事实 | 不应承担 |
|---|---|---|
| ShanmenCore | 基础类型、确定性 ID、内容版本身份；依赖 Core/CoreUObject | 玩法规则、库存和 World |
| ShanmenCombatCore | Action 快照、HitCandidate、DamagePacket、生命值上下文、有序防御层、Impact Ledger；有 GameplayTags，无 Engine/GAS 依赖 | Actor 查找、资产、直接扣库存、动画时序 |
| ShanmenItems | 定义/实例/容器/预留/事务回执；Repository、持久化及服务；无 Engine 依赖 | 技能直接计算命中，UI 私下更改数量 |
| ShanmenWorldGameplay | Entity Registry 与命中采集适配，有 Engine 依赖 | 根据几何事件自行形成第二套伤害权威 |
| ShanmenCombatRuntime | 动作与各能力运行契约，依赖 Engine、GameplayAbilities、GameplayTasks、CombatCore、WorldGameplay | 让 GAS 覆盖纯结算或物品真值 |
| demo_map | 现有游戏产品层、旧版本兼容、Run 组合根、UI/输入、Actor/World 执行、各系统宿主 | 继续把所有新能力堆入 GameMode；绕过下层事务 |

模块拆分方向正确，但尚不是“六个均匀、独立、低耦合的系统”。绝大部分生产代码仍在 demo_map；许多新契约也通过它完成产品组合。**下一步需要稳定模块间接口和所有权，不应仅为目录好看而大规模搬文件。**

## 3. 信息分区与数据权威

### 3.1 五类数据分区

| 分区 | 数据举例 | 所有者/生命周期 | UI 的角色 |
|---|---|---|---|
| 内容定义区 | 物品定义、动作定义、阵图、标签、版本戳 | 内容目录与配置；跨 Run 使用 | 显示名称、图标、说明，不能当玩家当前状态 |
| 持久真值区 | 实例数量、耐久、次数、容器位置、预留、处理过的请求 | ShanmenItems Repository/AuthorityService；GameInstance 级产品持有 | 读取投影，通过命令申请变更 |
| 成长/知识区 | 已学阵图、熟练度、角色成长 | 现有成长/存档权威；知识与熟练度 Adapter 单向读取 | 显示解锁和不足原因，不能直接赋予能力 |
| 局内真值区 | Run 身份、生命/状态、动作占用、灵力、部署与活动能力 | Coordinator 与各领域 Host/Session/Lifecycle | 显示当前值，不跨 Run 复用旧对象 |
| 展示/诊断区 | 血条插值、提示、图标、路径预览、动画音效命令、诊断回执 | UI/表现消费者；短期缓存，诊断可独立存档 | 可重建、可丢弃视觉缓存，但不能误删事务恢复证据 |

“同一资源只有一个权威”应按领域理解：物品数量归 ShanmenItems，生命/状态归相应战斗宿主，动作占用归仲裁器；不是把所有真值塞进一个超级对象。

Code A 和 Code B 仍存在于源码和历史场景中。0.0.10 物品 ADR 要求它们作为旧来源/兼容边界，而非两套在线物品权威。P1.14 已记录产品 Start/terminal cutover，当前 V3 observer 仍有 UsesShanmenItemLifecycle 防止旧写入的分支；但这不是对每一个历史调用点均不可达的全面证明。冻结索引须逐一列清在线入口、旧兼容入口与路由条件。新 UI 不得同时读取 Code A 数量、写 Code B 仓库、再调用新 Repository 扣款。当前实体实例 ID 必须贯穿仓库、携带、战斗消耗与撤离。

当前源码还有一个必须对 UI 讲清的实际区分：[Runtime 容器转移/拾取](../../Source/demo_map/demo_mapItemSubsystem.cpp#L2138) 仍会修改局内 Authority；[终局适配器](../../Source/demo_map/demo_mapShanmenRunLifecycleAdapter.cpp#L853) 则校验携入物和本 Run 新获物，将规范化结果提交给新持久权威。因此“局内拾取成功”不能直接显示为“已永久入库”。这说明局内状态与持久结果存在明确接缝，不足以证明全部旧入口已受约束，也不足以仅凭方法存在认定已发生双写。FZ-1 要审清可达入口、持久提交点及失败恢复；本报告不自行修改 ADR，把待审计的 Runtime 模型一概宣布为合法只读投影。

### 3.2 区间切换顺序

```text
局外仓库/整备
  → 校验实例与携带方案
  → Reserve：冻结资格，不代表已消耗
  → Commit/StartPreparedRun：形成持久证据
  → Run 根激活，World/运行宿主就绪
  → 局内命令与消耗
  → 撤离/死亡结算
  → 持久结果确认
  → 按所有者顺序清理 Run
  → 重建局外 UI 投影
```

进入关卡动画、点击“出发”或生成 Actor，都不能独自证明整条链已成功。失败后只重试未完成的同一请求；不以新 ID 重做已经成功的扣除。

P27.28 阵法散布发布已接入 GameMode → FormationRunLifecycle 的唯一入口。后续 P27.29/30 对结束路径作了补强：前置身份不匹配时拒绝；逻辑结束已成功但 World 清理被拒绝时，保留原成功结果与剩余 owner，重试只续清理，不重新扣资源。这个暂存结果仅属于同一 GameMode，不是磁盘 checkpoint；UI 不得显示可无条件离开或开启新 Run。这些是产品组合证据，不是新增物理输入或正式地图接线的验收。

### 3.3 时间、事件与刷新

- 现有 CombatRunFixedTimeline 消费 GameMode 的 DeltaSeconds，暴露 Run 绑定的整 30 Hz tick；**它不是整个游戏 30 FPS，也不证明所有系统锁步或联网确定性**。
- 权威时间负责动作窗口、护盾到期等判断；UI 可平滑插值，不得反向改变权威倒计时。
- 状态投影用于“现在是什么”；带身份的事件用于“发生过什么”。用事件重建动画，用状态修复晚加入或刷新后的 UI。
- 每个消费者独立记录已处理位置；关闭一个面板不应消费掉另一个面板需要的事件。
- 领域回执的持久确认与表现消费者的接收确认分开。展示 ACK 不是“动画/音效已真实播放”。
- 线程安全锁不是“异步”承诺；UObject/World 操作不能因引入后台存盘而被任意转移。

## 5. 游戏系统与“分级”的产品含义

### 5.1 五大体系不是五种伤害颜色

| 体系 | 玩家核心动作 | 必要准备 | UI 优先呈现 |
|---|---|---|---|
| 剑法 | 近战、时机衔接、格挡/闪避后继承、剑气 | 武器与动作配置 | 动作可用性、节奏窗口、强化来源、受阻原因 |
| 御器 | 携带真实器物，环绕/发射/控制 | 装备实例、灵力、部署资格 | 可控器物列表、活动/回收状态、资源 |
| 暗器 | 直投、弧投、瞄准与投掷 | 消耗物实例、数量、熟练度 | 数量、当前模式、路径、目标/落点有效性 |
| 阵法 | 空间布置、材料投入、启动与维持 | 阵图知识、材料、灵力、熟练度 | 阵图/锚点、缺料、范围、进度、撤销边界 |

最终伤害公式、境界倍率、经验曲线、货币统一口径和数值平衡尚不应在 UI 层提前固化。

### 5.2 当前可以引用的操作分级

- 阵法已存在 Beginner / Intermediate / Master 策略及 ProximityFill / RemoteThrow / ScatterFormation 三种操作。高等级保留下级能力；范围、时间、材料和 World 执行属于外层，不包含在等级枚举中。
- 暗器已有 Beginner / Intermediate / Master 请求分级；弧线规划对 Beginner 不开放。**Master 枚举存在并不证明“自动智能选路”已经完整落地。**
- 剑法、御器、术法不宜为了页面对齐而强行套用同一三级经验表。界面结构可以统一为“当前能力—下级/上级能力—解锁条件”，具体成长规则由策划与成长权威提供。
- 物品分类建议保持原需求中的原料/建造、战斗消耗、装备/灵器、知识/图谱四类；不要把灵矿、灵石、灵液提前显示成同一种已确定货币。

## 6. 面向 UI 的信息交互分区

### 6.1 页面分区及读写边界

| UI 分区 | 核心信息 | 允许命令 | 必须禁止 |
|---|---|---|---|
| 局外总览/仓库 | 资产、物品位置、状态、可用装备、知识 | 通过权威端口移动/选择/整备 | UI 拖拽成功就先改真实数量 |
| 出发整备 | 携带、部署、预留、缺失条件、Run 准备状态 | 校验、准备、取消、出发 | World 出现即显示持久提交成功 |
| 战斗 HUD | 生命、灵力、护盾、状态、快捷栏、动作可用性 | 发起一次有身份的能力请求 | 自行扣灵力、自行结算伤害 |
| 上下文交互/瞄准 | 落点、投掷轨迹、阵图锚点、目标、受阻原因 | Issue / Cancel；明确的 Retry | 将每帧预览当真实发射或消耗 |
| 物品/能力详情 | 属性来源、次数/耐久、模式与条件 | 查看、合法装备/使用请求 | 用显示文案决定实际抗性/能力 |
| 结算与恢复 | 战利品、损耗、已保存/待恢复状态 | 查询结果、重试同一未完成请求 | 为使页面好看而丢弃错误或重扣 |
| 开发诊断（独立） | Run/Request/Revision、回执、耗时/队列长度 | 受控诊断 | 将技术 JSON、哈希、协议信封塞进玩家界面 |

空间布局建议：中央保留瞄准/路径与危险可读性；生命/灵力/状态形成稳定区域；底部动作与快捷栏；边缘处理神识目标；临时提示短时出现。具体像素、画风、镜头、手柄与最终比例在原型阶段确定，不把现有 Canvas 坐标视为最终设计。

### 6.2 统一的 UI 状态契约（建议）

各页面至少可表达：

1. Loading / Unbound：数据未绑定，不能用零值假装资源耗尽。
2. Ready：展示带 Run/Owner/Revision 或 ProjectionId 的快照。
3. Pending：请求在处理，按钮防止重复提交，但不伪造结果。
4. Applied / Replayed：结果已按所属领域的成功规则证实，再更新投影。
5. Rejected / Stale：显示可理解原因；过期投影先刷新，不偷偷重新消费。
6. RecoveryRequired：结果不确定或持久权威需恢复；保留上下文，不退回“可再次购买/发射”。

典型事务：

```text
玩家点击
→ UI提交“动作+目标+当前投影身份”
→ Router检查新鲜度/可用性
→ 领域宿主执行，必要时调用物品事务
→ 权威结果与新投影
→ UI显示状态；表现消费者接收一次视觉/音效命令
```

剑气已有 ExpectedProjectionId 检查。Router 的 Dispatched 只说明调用发生，需进一步检查内层回执；新页面应继承这种区分。

### 6.3 刷新和缓存策略（建议，不是现状已全部满足）

- 数量、耐久、成长、权限：按 revision/变化事件重建小投影；不在每次 DrawHUD 中复制整份历史物品快照。
- 瞄准、屏幕坐标、血条平滑：按可见需求刷新；只更新必要字段。
- 提示与命令回执：事件驱动且有去重；UI 关闭/重开能从状态重新同步。
- 列表虚拟化/复用只影响显示控件，不改变物品实例和容器权威。
- 表现对象使用清晰所有者、失效检测和释放规则；缓存不得让旧 Run 的 Actor、Session、数据一直存活。
- 正常玩家只看原因与可执行选项，技术身份和原始错误进入诊断面板。

## 7. 数据计算、内存与性能风险

### 7.1 现在真正量到什么

既有 P27.28 完整根组日志在 **2026-09-14 03:08:30.367 UTC** 的启动采样显示：

| 指标 | 原日志数值 | 正确解释 |
|---|---:|---|
| 进程 Physical Memory | 628.29 MB used / peak | 此采样时的无头 UE 进程；不是完整运行峰值 |
| 进程 Virtual Memory | 648.35 MB used / peak | 日志所报进程虚拟内存指标；不能当显存 |
| 系统 Physical Memory | 22,012.75 MB used / 32,502.40 MB total | 整台机器，包括其他程序 |
| 系统 Virtual Memory | 50,906.70 MB used / 106,230.40 MB total | 整机指标，不能归到本项目 |

测试主体 03:08:43.986 UTC 才开始；运行参数包含 NullRHI、NoSound。因此该样本**不能证明实际地图、纹理、Niagara、音频、UI 或 VRAM 占用**。本次没有运行性能采样，也没有得到真实游戏平均/峰值 RAM、VRAM、Game Thread 或 GPU 帧耗时。

源码行数、20 MB 的模块 DLL、360 MB 的 Game exe、存档字节数，都不能直接等同于运行内存。

### 7.2 已确认的高优先级风险：物品历史与全量状态处理

源码入口：[快照导出与排序](../../Source/ShanmenItems/Private/ShanmenItemRepository.cpp#L1225)、[历史记录写入](../../Source/ShanmenItems/Private/ShanmenItemRepository.cpp#L1674)、[同步事务服务](../../Source/ShanmenItems/Private/ShanmenItemAuthorityService.cpp#L402)、[持久化与读回](../../Source/ShanmenItems/Private/ShanmenItemPersistence.cpp#L628)。本节按开头所列提交评估。

对当前代码的静态核验发现：

1. Repository 有 ProcessedRequests 历史映射，RecordProcessed 按请求加入。审计的 ShanmenItems 路径中未发现运行时裁剪/压缩或最大历史条数策略。ADR 也把历史清理留待以后；不能宣称“所有 Journal 都无限”，因为其他局部 Journal 有明确上限。
2. Repository.cpp 有 **26 个**“FState Candidate = State”拷贝代码位置，分布于不同命令/拒绝路径。**这是静态位置数，不是每个命令执行 26 次拷贝。**
3. CaptureSnapshot 会把五类映射导出数组，包括全部 ProcessedRequests，然后排序；不是廉价的引用读取。
4. ExecuteCommandLocked 保留 BeforeDocument、命令前快照与命令后快照，并在锁内执行持久化。Repository 与 Document 本身也持有各自的数据表示。
5. 持久化会校验/规范化、创建 JSON/字节、写临时文件、flush、读回校验、备份、替换和再次核对；大档时 CPU、临时内存与磁盘延迟会叠加。
6. 数据完全不变时有“不写盘”分支；但仍有规范化和磁盘读回校验，不能认为幂等重放完全无成本。
7. ValidateState 的部分路径按 intent 遍历历史事件，FinalizeRun 也有嵌套扫描。总体成本不是所有命令都 O(1)；某些检查随两组历史数量乘积增长。

**风险判断：** 这首先是“随使用量增长的状态和事务成本”，尚无证据把它诊断为实际内存泄漏或已经卡顿。当前 [产品物品 Subsystem](../../Source/demo_map/demo_mapShanmenItemAuthoritySubsystem.cpp#L287) 的 durable 命令明确要求 `IsInGameThread()`，随后直接调用服务并同步返回；服务在锁内完成快照与持久化。因此这条产品路径确实存在 Game Thread 等待保存的结构，大档写盘可能造成帧卡顿，实际耗时仍需测量。Mutex 只保证互斥，不代表工作已异步。

解决方向应先测再改：记录历史条数/字节和事务耗时；设计以完成 Run 为边界的归档/压缩方案；保留活动 Run、未决意图与重试必需证据。**不能简单 Remove 旧 ID、关闭校验或延迟成功确认来换性能，否则会破坏不重复消费和崩溃恢复。**

### 7.3 其他内存/计算热点

| 类别 | 代码事实或需测风险 | 后续处理方向 |
|---|---|---|
| 战斗 Impact Ledger | 每 Run 保存已接受的 GUID；有 Reset；大规模持续命中仍会增长 | 测量每 Run 峰值和结束释放；不按 UI 隐藏状态清理 |
| 防御纯结算 | 每次校验/排序防御层，构建索引数组和逐层回执；排序同 Order 时使用 GUID 字符串 | 先测命中频率×防御层数；必要时复用不可变排序结果，保持确定性 |
| Preview/Recovery | 部分结构有完整快照、身份和回执副本 | 核查生命周期和嵌套复制；不能把“值类型”理解为没有堆分配 |
| 有界 Journal | 暗器 ArcPreview OwnerSurfaceHandoffRecoveryJournal 明确最大 16 条，满时拒绝 | 内存有界仍需定义满载后的合法恢复/轮换，不能无限卡在拒绝 |
| 元数据与完整状态 | 剑法 Retry Journal Manifest 编码固定 48 bytes | 48 bytes 只是清单，不含下层完整 checkpoint，不代表恢复内存很小或已可独立落盘 |
| UI 投影 | 全量物品快照导出较重；高频读需要审查 | 小型只读投影、revision缓存、列表复用；本次未断言所有 UI 都在每帧全量复制 |
| World 对象 | 飞剑、弹体、阵法、标记、组件、特效增加对象与 Tick/GC 压力 | 统计活动对象、释放滞留、生成/销毁峰值；对象池也必须明确身份重置 |
| 资产与显存 | 无头日志不含正式渲染预算 | 单独测纹理、网格、材质、Niagara、音频和 UI 图集 |
| 同时构建/运行 | 编译器、编辑器、浏览器等共用整机内存 | 区分工具占用与游戏进程；不据整机占用购买硬件 |

### 7.4 估算模型：说明风险，不冒充实测

建议拆开记录：

```text
进程内存
= 引擎/模块基础
+ 资产与资源
+ 活动 World/Actor/组件
+ 领域真值和历史
+ UI/表现缓存
+ 同时存在的快照/序列化/读回缓冲
+ 分配器余量
```

若假设一条历史记录的平均总占用为 1 KiB，10,000 条约 9.77 MiB，100,000 条约 97.66 MiB；若某时刻有四份等量历史副本，对应约 39.06 / 390.63 MiB，尚未计 JSON、映射余量和资产。

这里的 1 KiB、四份都是**容量情景假设**，不是 sizeof 实测，也不是声明每条命令固定四份。真实值必须包含字符串、数组容量、容器桶与嵌套数据；只量 USTRUCT 的 sizeof 会低估。

### 7.5 后续性能采样与门槛建议

先不承诺最低配置。以同一台目标机、相同 build/地图/分辨率建立可重复基线：

| 场景 | 需要记录 | 验证目的 |
|---|---|---|
| 空场景 → 完整场景 | RAM、VRAM、对象数、加载峰值 | 分离引擎、资产和功能成本 |
| 物品 1k/10k，历史 1k/10k/100k 梯度 | 命令 P50/P95/P99、快照/保存时长、峰值临时字节 | 找增长曲线与同步卡顿 |
| 连续命中、御器、暗器、阵法同时活动 | Game/Render/GPU 耗时、分配速率、对象峰值 | 检验真实规模，而非仅单个对象 |
| 连续 20 次开始/结束 Run | GC 后存活对象、领域记录、RAM趋势 | 区分缓存高水位和不能释放的泄漏 |
| 所有 UI 面板反复开关、改变分辨率/输入设备 | UI时间、布局、过期引用、焦点和订阅数 | 确认展示层不会积累状态 |
| 中断/重开/存盘故障 | 文件恢复、次数/数量、重复副作用 | 优化不能破坏数据可靠性 |

建议以 60 FPS 的 16.67 ms 作为首轮讨论目标，不是当前已达到的指标；UI 更新初始预算可设 P95 ≤ 1 ms、P99 ≤ 2 ms，目标机确认后再冻结。交易若不能进入对应帧预算，应明确 Pending 体验与受控执行策略，而非先扣再补。

长期运行验收应看 warm-up/GC 后趋势，不要求内存瞬间回到精确初始字节。需要分别记录 RAM、commit、VRAM 和各线程耗时，不能拿一个“总内存”指标代替。

首轮接线的责任分配如下。它是基于现有模块的准备表，不是新增一套服务或改造授权：

| 数据/交互 | 现有接入边界 | 给 UI 的信息 | 接线前必须回答 |
|---|---|---|---|
| 仓库、携带、次数/耐久 | GameInstance 持有的 ShanmenItemAuthoritySubsystem → AuthorityService | 当前实例与容器的精简只读投影、权威修订号 | 是否已绑定正确 Profile，哪些操作有持久成功证明 |

| 攻击/防御/能力按钮 | 已有能力 Router/Host 与动作仲裁 | 可用性、当前资源、受阻原因、投影身份 | 外层“已分派”是否得到内层成功；重复输入采用什么身份 |
