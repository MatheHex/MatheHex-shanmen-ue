## 3. 携带筛选和损失边界

产品层从当前唯一物品快照构造冻结清单。必须已装备武器、护具和普通背包；缺哪一项就显示具体条件。丹药可以自行选择携带，不额外强制数量。

| 整备位置 | 是否进入普通清单 | 当前已验证的权威行为 |
| --- | --- | --- |
| 已装备武器、护具、普通行囊 | 是，DeploymentLock | 撤离保留原身份；死亡成为损失墓碑 |
| Carry 中物资 | 是，整堆 Quantity | 撤离只返还已确认的未消耗余额；死亡损失 |
| Carry 中备用装备 | 是，DeploymentLock | 不因未装备就绕开普通损失 |
| 安全格装备、已确认安全格内容 | 否 | 不进入普通损失清单，测试验证死亡后原身份／数量／位置保持 |
| 局外仓库、测试钱包 | 否 | 留在局外，不通过探索清单扣除 |

以上死亡与撤离是隔离自动化中的真实事务证据，不是玩家完整流程证据。局内安全格使用、丢弃和移动尚未开放；后续必须经 Run 命令确认扣除，不能把“保留”理解成无限消耗。完整分区见 [携带与 Run 边界](../Demo20/CarryAndRunBoundary.md)。

## 4. 一次持久保存与精确重试

新增 StartLoadoutDurable 沿既有 GameInstance Subsystem → AuthorityService → Repository → 原子存盘执行。中间 Reserve 只在候选 Repository 中产生，最后调用已有 StartPreparedRun；任何后续行拒绝或可确认回滚的保存失败都丢弃整份候选，不发布半套预留。

成功新增一个存档代数，而不是每件物品保存一次。已有 Reserve 与 StartPreparedRun 回执全部保留供审计，权威 revision 因多条内部命令推进，但磁盘只发布一次。没有新事务枚举、第二份数量权威或新存档格式，仍为 schema 6。

批次身份从 Owner、整备 Scope、内容戳和冻结 revision 派生；行身份从批次和物品身份派生，数组顺序不影响结果。重试既检查启动指纹，又核对每行 Reserve 指纹。合法改量、改用途或改物品版本不能重放原成功；非法 DeploymentLock 数量直接拒绝。新批次不能接管其他路径创建的预留，也不能遗留待提交准备。

## 5. 恢复投影与命令分区

InspectActive 从持久启动回执识别未结算 Run，核对 Demo2.0 携带用途和 Owner／Scope。数量由预留量减去已确认的直接消耗、已提交 Quantity Intent 得出；取消不扣除。尚未完成的 Quantity／资源 Intent 返回明确恢复原因，不假定免费使用。

## 6. 界面和计算内存边界

携带摘要仅在快照刷新时计算并缓存，Paint 不构建 Repository 或遍历历史账本。玩家主界面不展示技术 ID、指纹或种子；开关面板本身不启动 Run、不扣除物品。

真实 720p 首轮发现长句与装备标题重叠，修为背包下方两行摘要后重新双目标构建与实际核验。最终候选两种分辨率均未观察到该重叠；卸下护具显示“请先装备护具”，重装后恢复 3 件普通装备／8 件物资、安全格 1 件。

出发候选仍复制权威快照，公共批次最多 256 行；恢复和准备锁会扫描历史回执。缓存只避免每帧重复计算，不能代表整个内存问题解决。本轮未测正式探索帧耗时、峰值内存或多轮对象释放，不用 JSON 大小或构建时长代替 M5 实测。新 Items 核心文件没有 demo_map、UWorld、AActor、ApplyDamage 或 RNG 依赖，模块仍无 Engine 依赖。
