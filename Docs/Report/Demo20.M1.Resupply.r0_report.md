# 山门 Demo2.0 M1 有限基础补给 Report

## 1. 结论与范围

本轮完成正式死亡后有限基础补给的权威事务、持久化和整备按钮，并修正终局丢失背包装备后容量没有同步关闭的问题。最终改动驱动回归 209 Success／0 Fail，Editor／Game 双目标原生退出 0。实际 Standalone 在 1280×720 和 1920×1080 验证了新档拒绝、重复点击、面板返回与重启不重发。

这是 M1 的补给增量，不是正式探索或完整 Demo2.0 完成。自动化通过真实 Reserve → Start → Death 端口证明死亡后的补给；实际玩家路径目前只能证明无正式死亡时明确拒绝。正式 Run 出发、探索、治疗、随机搜集、终局与原局恢复仍须接线和真实验收。

完整范围以 [探索 Goal](../Prompt/Demo20.Expedition.goal.md) 为准，剩余项目见 [阶段状态](../Demo20/ExpeditionStatus.md)，原始日志路径、SHA-256 和失败证据见 [Development Log](../Log/Demo20.M1.Resupply.r0_log.md)。

## 3. 补给规则与唯一权威

整备按钮由 GameMode 读取当前权威快照，固定产品目录生成申请，沿既有 GameInstance Subsystem → AuthorityService → Repository → 原子存盘链执行。UI 不传任意发物列表、不拥有补给次数、不直接改数量或钱包。

必须存在同 Owner、同整备作用域的最近成功 Death 终局，且不能已准备／开始下一局。撤离、伪造请求 ID、其他 Owner／作用域、过期 revision 和待提交预留均拒绝。

| 检查范围 | 确实缺失才发放 | 位置 |
| --- | --- | --- |
| 整个 Owner 的任意武器 | 青锋剑 1 把 | 武器槽 |
| 整个 Owner 的任意护具 | 素纹道袍 1 件 | 护具槽 |
| 整个 Owner 的任意普通背包装备 | 基础行囊 1 个 | 背包装备槽 |
| 整个 Owner 的回春丹 | 回春丹 2 枚 | 局外仓库 |

仓库中的替代剑、护具和大包同样算拥有；卸下或移动不能变成缺失。已有丹药不补齐到两枚。不发货币、高级装备、材料、战利品或第二个护命匣。详细规则见 [有限补给政策](../Demo20/BasicSupplyPolicy.md)。

## 4. 有限领取与持久幂等

每个已确认死亡最多执行一次非空补给。申请身份由 Owner／作用域／死亡／政策派生，新物品身份由 Owner／作用域／死亡／定义派生。重复点击、当前 revision 重试、行顺序变化及原生重启返回原回执，不产生新物品或新存档代数。换政策也不能对同一死亡再领取。

全套已有时拒绝且不消耗机会。缺失检查、物品生成、合法位置、容量和领取回执一次提交；后续行失败不保留前面的候选发物。注入 AtomicReplace 失败时完整文档回滚，同身份重试仍可成功。未确认持久结果时 UI 显示未保存或恢复中，不报告成功。

## 5. 终局容量与兼容

FinalizePreparedRun 在同一终局候选中协调储物容量。背包装备成为损失墓碑后，空 Carry 变为禁用 1×1；重新补给基础行囊时恢复 6×4。若仍有未处理内容，拒绝整个终局，不删除内容来满足容量校验。旧无 Grid 快照保持原兼容路径。

本轮没有新增存档字段或提升 schema，仍为 schema 6。追加操作和错误枚举，沿用既有回执的死亡关联与发物 ID 列表；加载验证要求一次死亡仅一个补给、确定性申请／物品身份和合法死亡关联。旧 schema 迁移测试随 Items 根运行，但不声称旧二进制能读取新增操作。

安全格测试只证明未投入该测试 Run 的护命匣与玉佩未被误删，不能替代正式玩家出发筛选和死亡保留验收；这部分仍属 M4。

## 6. 计算与内存边界

每次补给至多四行，检查全 Owner 库存和既有历史回执；候选、预览和持久验证仍会复制快照。加载验证用死亡 ID 集合检查重复补给，没有再增加历史两两扫描。物品布局沿用有界占格检查。

以上是实现范围，不是运行性能结论。本轮未测帧耗时、峰值内存或多轮对象释放；不能以序列化文件大小、理论复杂度或构建时长替代 M5 的真实性能验收。新补给核心文件无 demo_map、UWorld、AActor、ApplyDamage 或 RNG 依赖，Items 模块仍无 Engine 依赖。
