## 3. 玩家规则与产品接线

快捷栏第一键读取既有输入注册表，默认数字 `1`。仅存活的正式探索角色、非满生命且无不兼容动作时可用；满生命、死亡、格挡、出剑／闪身／用药恢复期间拒绝。一次恢复最多 35 生命，上限 100，用药恢复 0.6 秒；这些是阶段参数，不是最终平衡。

选择顺序为普通携带优先，其次已装备护命匣的安全格，同类按稳定物品身份排序。普通数量从启动和已确认消耗回执重建，不能读整备中已部署的零数量墓碑；安全格读取同一物品文档。仓库不属于局内可用物资。没有药时明确提示出发前携带。

HUD 缓存普通／安全格数量，在出发、恢复和命令确认后刷新，不在 Paint 遍历历史。待确认期间隐藏旧可用数量，显示恢复提示；只有扣药与治疗后的世界记录确认后才显示使用成功。石庭练习不调用持久用药。

## 4. 唯一权威与生命变更

普通携带使用既有 PreparedRunQuantityIntent 预备／提交，安全格使用同一 AuthorityService 的 ReserveDurable／CommitDurable。新增产品协调器仅绑定这些既有端口，没有库存实现，没有准备 EditGrid 旁路或旧 Code A／Code B writer。先识别唯一活跃 Run；未结算探索仍锁定整备。

生命变更调用 VitalityAuthority 的薄端口 TryCommitExternalMutation，校验预期 revision 后交给既有 CommitLedger。伤害、治疗和旧 Impact 重放共享账本，不重建另一套生命状态；候选生命直到持久确认才对 UI 发布。新测试证明伤害后治疗保留原 Impact 账本，旧攻击重放不再次伤害治疗后的生命，新攻击仍能正常结算。

当前只支持出发原携带和安全格丹药。本局新领取的药品必须在 M3 接入正式来源／领取端口后才能使用，不能靠放宽整备锁或回退旧库存来补齐。

## 5. 固定用药意图与恢复

顺序为保存世界用药意图 → 同一物品权威确认扣除一颗 → 保存治疗后的生命与动作序号 → 发布 Session 和 HUD。意图绑定 Run、下一动作序号、物品身份、预期数量、物品版本与来源；确定性身份不依赖帧数、打开 UI 次数或临时请求 GUID。

首次世界保存失败时不提交扣药；结果不确定时保留原候选并暂停。扣药后世界保存失败则保留同一意图，重试／重启只向前完成，不换选另一颗药、不退款已确认消耗、不提前恢复生命。启动先只读识别 Run，再恢复待确认意图，最后读取严格余额，不能让未完成 Quantity Intent 被当作可用数量。

安全格最后一颗药提交后会清除父容器。恢复仅允许精确匹配已提交 reservation 的该物品墓碑继续：请求、物品、预期版本、用途、Owner／Scope、资源类型和数量均校验。不能因为安全格出现另一颗药就重选，也不能因父容器已清空永久阻塞已扣药意图。

## 6. 兼容和数据成本

物品 schema 仍为 6，原无用药意图的世界记录保持 333 字节原编码与 CAS；待确认用药增加有标记的可选 33 字节尾部，总长 366。治疗确认后回到原编码。未知尾部失败关闭，不猜测迁移。尾部的预期数量仅是请求前置条件，不是物品余额或第二份数量权威。

恢复语义由 Medicine.r1 确定，当前固定 35 生命与 0.6 秒；以后调整公式必须处理旧待确认意图的语义兼容，不能直接用新规则重算旧消费。世界记录继续既有内容戳、长度上限、摘要和精确旧字节 CAS。

HUD 常驻仅缓存两个数量整数；命令仍会复制世界候选、物品快照并扫描回执，且治疗要串行确认世界与物品保存。333／366 字节是序列化体积，不代表实际运行内存或帧耗时。同步存盘卡顿、多轮对象释放和历史账本增长尚须 M5 实测，不能据文件小宣称性能合格。
