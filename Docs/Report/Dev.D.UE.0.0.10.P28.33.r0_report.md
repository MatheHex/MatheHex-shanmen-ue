# Dev.D.UE.0.0.10.P28.33.r0 Report

## 1. 本轮范围

从 `dedff598ec7b14f14af647056af8f37c239686e3` 的无损来源 codec 继续，接入既有 Repository → AuthorityService → AuthorityDocument：来源计划、来源接收回执、序号与保底前后事实随库存同文档保存。没有独立奖励文件、第二库存或旧写入旁路。本轮不切换 Manager 的生成入口，不创建 World 容器，不把来源物品提前插入库存图。

## 3. 接收、重放与终局

首次来源要求真实 StartPreparedRun/ClaimPreparedRun 的归属证据且 Run 未终局；按现有每 Run 保底语义从 cursor=0、pity=0 开始。随后来源要求连续序号、精确保底前值和相同来源内容印记。序号与保底从不可变历史推导，不另维护一个可漂移的可变账本。保底数值在本层只检查结构与前后连续性，不硬编码现有某一策略的 0–3 数值范围。

Owner+Run+SourceRole 派生来源稳定键；同来源完整计划相同则重放原回执，不推进文档代数。计划冲突、旧 cursor、错误保底前值和内容漂移失败关闭；同一服务内并发请求串行化。终局后允许精确重放已接收历史，拒绝新来源。此处只证明来源历史与已有终局共存，不声称已闭合获物/消费/遗失/撤离的产品组合。

目录授权是明确的有限保证：请求的 ItemContent 必须等于权威目录印记，每项 Definition 必须与已存在目录完全相等；本轮不允许来源偷偷扩充目录。来源 manifest 与各策略 ID 仍由未来可信生成 Adapter 解析与授权，首次成功来源只固定该 Run 的来源内容印记。没有把任意合法字符串当成“已通过产品策略注册表验证”。

## 4. 失败恢复与旧档迁移

来源接收沿既有临时写入、校验、备份、替换路径执行。写前失败恢复精确旧文档，来源查询不可见；替换后回读结果不确定时，重开确认完整 after-state 才返回持久成功；无法确认则沿原机制进入 RecoveryRequired。调用者必须检查 `IsCommandSuccess()`，不能只看候选 `Receipt.IsSuccess()`。

schema 1/2 先按原字段形状验证旧 SnapshotDigest，再在内存升级到 schema 3；schema 2 旧摘要排除 GeneratedSources，schema 1 同时排除历史上不存在的 RewardMetadata。保留旧 InitialSnapshotDigest 与迁移来源证据，后续显式打开只规范化一次，不因新增字段重导入库存。非零奖励元数据是 schema 2 迁移的保持基准；schema 1 既有元数据补齐规则不扩展到 schema 2。未来版本仍拒绝降级恢复。

新来源大整数使用专用字符串 codec，未全局替换历史 Items.RewardMetadata 的反射数值编码；其超大整数精度风险仍需在后续来源物品进入库存链前处理，不能宣布全存档整数问题已解决。

## 5. 容量、计算和 UI 接口边界

单来源沿用 1024 条上限；整文档最多 4096 来源、65536 来源条目，加载在复制候选前累计检查。原始文件用同一文件句柄先核对长度，超过 64 MiB 不分配载荷缓冲；解析前拒绝重复键及超过 64 层嵌套。编码也拒绝超限输出。历史不能因达到上限就静默删除幂等证据，超限按失败关闭处理。

**这些不是运行内存或吞吐量验收。** 输入、候选状态、前后快照、JSON DOM、UTF-8/文本和文件回读可能同时驻留；当前仍沿既有锁内全量保存与全历史校验，来源检查会扫描回执并重算指纹。规模梯度、长时内存和锁持有时延尚未实测，不以 64 MiB 文件限制宣称 RAM≤64 MiB。UI 后续应请求按身份的只读摘要，不把整份历史当显示模型或持有第二份可写权威。
