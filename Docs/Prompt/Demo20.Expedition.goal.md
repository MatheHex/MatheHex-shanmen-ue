一、开发目标
基于《山门》当前代码框架和 Demo2.0，制作一个本地 UE 内可实际游玩的单关探索 Demo，完成以下完整循环：
新档初始化 → 局外仓库与整备 → 携带装备和消耗品出发 → 战斗、搜索与随机掉落 → 格子背包整理与取舍 → 成功撤离或死亡 → 保存结果 → 返回整备并再次出发。
本阶段重点是让已经研究的背包、储物装备、掉落、随机性、安全格和物品权威在真实游戏中形成连续体验。
玩家必须能够通过正常界面和键鼠操作完成整个流程。不得依赖控制台命令、调试发物或手工编辑存档完成验收。
交付形式为本机 Unreal Editor 的 PIE／Standalone 可运行工程，不要求 Cook、Package 或独立安装包。
二、已确定的开发边界
本阶段采用以下范围：
1. 一张小型探索关卡，由数个相连区域、战斗点、宝箱和撤离点构成，目标单局约 10–15 分钟。
2. 二维格子背包，物品具有不同占格尺寸，支持旋转、移动、拆分和堆叠。
3. 物品包含武器、护具、治疗消耗品、材料／战利品和储物装备。
4. 敌人死亡产生可搜索的尸体或掉落容器；场景有宝箱；支持主动丢弃物品及重新拾取。
5. 使用固定地图布局，随机生成掉落种类和数量、敌人组合及宝箱位置。
6. 成功撤离带回合法携带物品；死亡损失普通携带物品；安全格内物品死亡保留。
7. 局外提供仓库、物品存取、装备选择、消耗品携带和再次出发。
8. 测试阶段提供高额测试货币。默认新测试档一次性获得 1,000,000 测试货币，数额可配置。
9. 战斗包含基础剑法、闪避、格挡、治疗、两类普通敌人与一个精英敌人。
10. 继续使用中文功能界面与占位美术，优先完成操作清晰、状态可信的完整流程。
本阶段不包含联机、多关卡、随机地图布局、随机装备词条、宗门经营、完整商业经济、商店买卖、制作强化、五大战斗体系全面展示或发行级美术。
测试货币不自动扩大为商店系统需求。已有御器、暗器、术法和阵法框架保留，但不以它们的完整展示作为本阶段完成条件。

- 现有物品唯一权威、背包、储物装备、来源授权、掉落计划、随机种子、Run 生命周期、持久化和恢复的设计与实现。

采用以下优先顺序处理规则：
1. 本 Goal Prompt 中明确确认的阶段边界。
2. 用户此前已经确认、且与本阶段不冲突的具体规则。

保留现有用户未提交修改和未跟踪文件。仅提交本阶段实际产生的文件。
四、关卡与玩家流程
建立一张新的小型探索关卡，延续 Demo2.0 的独立入口和视觉方向。关卡至少包含：
- 一个清楚、安全的出生区域。
- 三个以上相连的探索或战斗区域。
- 普通敌人战斗点。
- 一个精英敌人所在区域。
- 分布于候选位置的可搜索宝箱。
- 一个清楚可识别、可到达的撤离区域。
地图几何布局固定。随机内容从预先检查过的候选位置和敌人组合中选择，确保出生点、通路、交互距离和撤离点不会因随机结果失效。
玩家可以选择继续搜集或提前撤离。默认撤离点从开局可用，精英敌人提供更好的搜集机会，不强制清空全图才能撤离。
进入撤离区域后显示明确提示，玩家主动交互开始撤离。撤离读条可以被离开区域或受到伤害打断；默认读条约 3 秒，属于可调整参数。
五、背包与储物装备
5.1 格子背包
实现实际可操作的二维格子背包：
- 不同物品具有明确的宽度、高度和最大堆叠数量。
- 支持拖放、旋转、拆分、合并、移入容器和移出容器。
- 放置前展示有效或无效预览。
- 空间不足、位置冲突、物品不兼容时给出具体原因。
- 失败操作保留原物品位置、数量和身份。
- 部分堆叠成功时，剩余数量保持在原来源中。
- 默认提供便捷转移操作，减少反复拖动；具体键位读取现有输入注册表。
默认不引入重量限制，容量取舍主要由占格面积和堆叠上限产生。
5.2 储物装备
本阶段实现两类储物装备：
- 普通背包装备：决定局内普通背包的格子容量。
- 安全格装备：提供少量死亡保留空间。
至少提供两种容量不同的普通背包，使玩家能够实际看到储物装备的作用。安全格默认只提供一种基础规格。
储物装备更换默认在局外整备中完成。更换为较小容量时，必须先妥善处理无法容纳的内容，不能静默删除、溢出或复制物品。
本阶段默认禁止储物装备嵌套。具体尺寸沿用已有已确认研究；若未有定案，可使用以下初始参数：
- 基础背包：6×4。
- 扩容背包：8×5。
- 基础安全格：2×2。
这些是阶段调试参数，不代表最终游戏平衡。
5.3 安全格
安全格规则必须在整备与背包界面中清楚可见：
- 默认允许放入治疗消耗品、材料和普通战利品。
- 默认禁止放入武器、护具和储物装备。
- 安全格中的物品仍属于唯一物品权威，使用后照常扣除。
- 成功撤离时内容带回。
- 死亡时保留死亡发生时已经确认放入安全格的内容。
- 重复死亡结算或恢复请求不得重复保留、重复返还或复制物品。
安全格装备本身作为持久装备保留，普通背包装备默认随死亡损失。
六、物品内容
本阶段至少提供一组足以支持搜集取舍的物品目录，建议总数为 10–15 个定义，包括：
- 至少两种可装备武器，沿用基础剑法操作。
- 至少两种可装备护具，实际影响已有防御计算。
- 至少一种可使用的治疗消耗品。
- 数种占格尺寸、堆叠上限不同的材料和战利品。
- 两种普通背包及一种基础安全格。
物品名称、图标或占位图形、类型、占格尺寸、数量和用途说明完整。
本阶段武器与护具属性按固定定义配置，不新增随机词条系统。材料和战利品可带回仓库，制作或出售用途可以留待后续。
治疗需要满足以下条件：
- 非满生命时能够实际恢复生命。
- 消耗和治疗结果经现有权威流程确认。
- 满生命、角色死亡、物品不足或正在执行不兼容动作时有明确反馈。
- 重复点击和中断处理不得导致免费治疗或重复扣除。
- 本局新拾取的合法治疗物品能够使用；若既有整备限制阻塞此路径，应接通正式端口，不能恢复旧库存旁路。
七、掉落、搜索与丢弃
7.1 敌人掉落
敌人死亡后生成可搜索的尸体或掉落容器。
- 每个敌人来源具有稳定身份。
- 同一死亡事件只能产生一次掉落结果。
- 容器内容与实际领取状态一致。
- 反复交互、重新打开、离开后返回或恢复游戏，不得重新生成物品。
- 领取成功后，来源中的物品同步减少或消失。
- 空容器保留“已搜空”状态，避免误导玩家。
7.2 宝箱
宝箱从关卡候选位置中随机选取并生成。
默认首次搜索需要短暂读条，完成后显示内容；同一局已搜索容器再次打开时立即显示。搜索期间仍可能受到敌人攻击。
具体读条时间可调整，默认约 1 秒。搜索中断不领取物品、不重抽掉落。
7.3 主动丢弃与重新拾取
玩家可以从普通背包或安全格主动丢弃允许丢弃的物品。
- 丢弃后形成可见、可交互的世界物品或容器。
- 保留原物品身份和正确数量。
- 重新拾取回到同一物品权威。
- 拾取失败时物品继续留在世界中。
- 丢弃与拾取的连续操作不能复制物品。
- 主动从安全格丢出的物品不再享受死亡保留。
八、随机性
每局创建独立 RunSeed。使用现有确定性随机实现与稳定来源身份，为以下内容生成结果：
- 敌人组合。
- 宝箱候选位置。
- 掉落物品种类。
- 掉落数量。
随机规则必须满足：
- 相同内容版本、种子和来源输入得到相同结果。
- UI 打开次数、帧率和无关操作不能改变掉落。
- 恢复原局时继续使用原种子和已经接纳的结果。
- 同一来源只接纳一次生成计划。
- 不同来源的随机结果不因交互先后顺序而意外互相影响。
- 新一局可以产生不同结果，同时保证关卡仍可完成。
生成结果通过已有来源计划、授权和物品接纳端口进入物品权威。世界 Actor 负责表现和交互，不直接创建另一套物品数量真值。
随机种子、来源标识和诊断信息保存在开发日志或专用调试界面，玩家主界面使用正常物品与交互说明。
九、局外整备、死亡和持久化
9.1 局外整备
提供以下正常界面操作：
- 查看仓库。
- 在仓库、普通背包、安全格之间转移物品。
- 装备武器、护具、普通背包和安全格。
- 选择携带治疗物品。
- 查看容量和出发条件。
- 开始新一局。
新测试档通过正常初始化获得一套基础装备、少量治疗物品和高额测试货币。
高额货币只初始化一次，重复进入整备、重启或恢复不能反复叠加。界面明确标注测试货币。
本阶段不要求商店。为避免死亡全损后无法继续，整备界面提供基础补给领取：
- 仅在缺少必要基础装备时补足对应物品。
- 不无限重复领取形成可囤积资源。
- 基础补给足以再次出发。
- 补给通过正式物品命令进入唯一权威。
9.2 成功撤离
成功撤离后：
- 普通背包、安全格和已装备物品按规则带回。
- 仓库或返回后的携带容器能够容纳结果；不能因为仓库空间不足静默丢弃物品。
- 显示本局取得、消耗及带回物品。
- 保存确认后显示完成状态。
- 重复请求不得重复发放战利品。
9.3 死亡
死亡后：
- 普通背包内容、武器、护具及普通背包装备损失。
- 安全格装备和安全格中已确认的内容保留。
- 局外仓库保留。
- 显示损失和保留物品。
- 保存确认后返回整备。
- 本阶段不要求返回上一局找回尸体。
9.4 意外退出与恢复
正常暂停退出或意外关闭后，下一次启动能够恢复原局的已确认状态，至少包括：
- Run 身份与随机种子。
- 玩家已确认的物品与容器归属。
- 已生成、已搜索和已领取的来源状态。
- 已消耗物品。
- 已击败敌人与已完成终局状态。
- 继续游戏所需的玩家位置、生命及关卡状态。
具体恢复粒度依据现有持久化能力实现，并在报告中明确。不得通过重新生成掉落、返还已经消耗物品或重新结算来伪造恢复成功。
存盘失败或结果不确定时展示明确提示，允许安全重试或恢复；未确认成功前不得显示“已带回”或“已保存”。
开发和验收使用 Demo2.0 隔离测试档。
十、战斗与敌人
在现有基础剑法、闪避和格挡上接入治疗，并实现：
- 一类普通近战敌人。
- 一类普通远程敌人。
- 一个具有清楚攻击预警的精英敌人。
敌人具备完成本关所需的发现玩家、接近或保持距离、攻击、受击和死亡行为。
战斗调试以支持探索循环为目标：玩家能够识别危险、处理普通遭遇、使用治疗，并决定继续搜集还是撤离。精英敌人具有更高风险和更好的掉落机会。
实现必要的命中、受击、死亡、治疗和拾取反馈。允许使用占位动画、简单音效和基础特效，但攻击范围、交互范围与显示预警应一致。
十一、UI 与输入
形成五类连续可用的界面：
1. 局外仓库与整备。
2. 战斗 HUD。
3. 格子背包及装备。
4. 尸体／宝箱／地面物品搜索与转移。
5. 暂停、恢复提示和结算。
界面要求：
- 中文文字、统一颜色与按钮状态。
- 物品尺寸、堆叠数量、装备状态和安全格规则可理解。
- 背包满、目标位置冲突、物品不可使用等拒绝原因具体。
- 处理中、成功、拒绝和恢复中状态可区分。
- UI 以权威确认后的状态刷新。
- 拖放失败后界面恢复到正确位置。
- 键位提示读取现有输入注册表。
- 窗口失焦、面板切换、拖放取消、返回和恢复不会遗留移动、攻击或格挡状态。
默认打开局内背包或搜索界面时，世界继续运行；玩家停止移动与攻击，敌人可以继续行动。Esc 暂停菜单暂停单机游戏。需要实际验证两者的输入和计时行为。
十二、实现约束
复用当前领域模块、确定性身份、物品权威、持久化、Run 生命周期和已存在的恢复机制。
- 所有物品变更通过现有唯一权威命令端口。
- UI、敌人、宝箱和地面 Actor 只提交意图及展示结果。
- 不在 Demo2.0 中增加另一份库存、货币或物品数量权威。
- 不因正式端口拒绝而自动退回旧 Code A／Code B 写入路径。
- 持久操作和世界表现必须处理部分成功、重复请求和恢复。
- 优先修复会阻塞本阶段玩家流程或导致复制、丢物、坏档的结构缺口。
- 存档格式与公共接口调整应有明确必要性和兼容处理，避免为单一界面新建大规模框架。
十三、阶段实施顺序
按以下里程碑推进，每个里程碑完成后交付 Report、Development Log 和 GitHub 链接：
M1：持久整备与格子背包
完成隔离新档、仓库、装备、普通背包、安全格、高额测试货币、基础补给和出发入口。
M2：探索关卡与战斗基础
完成固定小型关卡、两类普通敌人、精英敌人、治疗和可用撤离点。
M3：随机来源与搜集交互
完成随机敌人组合、宝箱位置、掉落计划、搜索、领取、丢弃、重新拾取和容量取舍。
M4：撤离、死亡与恢复
完成带回、普通物品损失、安全格保留、保存失败提示、重复请求处理和原局恢复。
M5：完整游玩验收与交付
修复真实操作发现的问题，完成完整循环、界面检查和性能观察，交付阶段基线。
允许根据依赖调整内部开发顺序，但应尽早形成可观察的玩家流程，避免长期只增加底层接口。
十四、验收标准
本阶段完成必须同时满足：
1. 隔离新档通过正常界面获得初始配置并出发。
2. 背包可完成旋转、移动、拆分、合并、装备和跨容器转移。
3. 不同容量背包实际生效；小背包替换时不会丢物。
4. 敌人与宝箱正常产生随机掉落，已领取内容不重复出现。
5. 背包满、部分堆叠和非法放置保持正确数量与归属。
6. 主动丢弃再拾取不复制物品。
7. 玩家通过真实键鼠完成战斗、非满生命治疗、搜集和成功撤离。
8. 完成一次死亡，普通物品损失、安全格保留、仓库不受影响，并能再次出发。
9. 重启后整备和结算结果保持；恢复原局不重抽掉落、不返还已消耗物品。
10. 重复点击、重复领取和重复终局请求不重复执行。
11. 存盘失败或恢复中有正确提示及可继续的处理路径。
12. 在 1280×720 和 1920×1080 下，主要界面无遮挡、关键文字可读、拖放和焦点正常。
13. 记录本机真实帧耗时、运行内存和多轮开始／结束后的对象释放趋势，修复影响操作的卡顿与明显持续增长。
