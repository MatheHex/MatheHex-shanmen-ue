# 上半部分：只读背景与策划边界

## 1. 版本定位

`Dev.D.UE.0.0.9B` 是 0.0.9 的第二次开发方向。

本版本从 `Dev.D.UE.0.0.8` 的稳定镜像重新开始，不延续原 `Dev.D.UE.0.0.9` 的实现。原 0.0.9 已终止并作为历史归档处理，其代码、地图、怪物、UI、数据、测试、临时修复和未完成系统均不得自动并入 0.0.9B。只有未来策划针对某一项成果单独确认后，才可重新设计并选择性引入。

`0.2 final report.docx` 仅用于理解项目早期演进和通用工程习惯，不是 0.0.9B 的继承基线，也不能覆盖 0.0.8 的当前事实。

## 2. 0.0.9B 核心方向

本版本集中建立《山门》自己的类塔科夫物品管理框架：

> 备战整理 → 进入地图 → 搜索容器与尸体 → 转移、装备和管理物品 → 撤离 → 同一批真实战利品进入局外仓库。

重点是统一的物品实例、容器位置、事务逻辑、UI 结构和物品信息表达，不是继续扩充地图、怪物或美术内容。

当前优先采用全部 `1×1` 单格物品。多格、旋转、不规则形状、复杂重量、无限嵌套和多人权威只保留扩展空间，不属于首轮实现压力。

## 3. 技术分析的使用方式

《Dev.D.UE.0.0.9B 类塔科夫背包、仓库与搜索系统技术分析报告》是本版本的架构参考，核心原则包括：

- 每件物品只有一个真实实例和稳定 ID；
- 每件物品在任一时刻只有一个真实父位置；
- 仓库、装备栏、玩家储物、尸体、普通容器、地面和结算尽量共用统一数据与转移入口；
- UI 负责展示和提交操作，不成为物品数据权威；
- 空间道具本体稳定引用其内部容器；
- 快捷栏只引用真实物品，不复制物品数量；
- 奖励生成与搜索揭示分离；
- 撤离、死亡和放弃只允许一次终局结算。

报告中的示例类名、结构体、标签和分层不是唯一强制实现。Codex 可根据 0.0.8 的真实工程采用更合适的实现方式，并在 Report 中说明关键差异与原因。

## 4. 本任务边界

本任务只负责接收、隔离、构建验证和现场盘点，不开始 0.0.9B 的正式 P 阶段功能开发。

本任务不要求：

- 实现新的物品 Repository 或事务服务；
- 重写现有背包、搜索、装备、仓库或存档；
- 制作新的仓库、背包、Loot 或详情 UI；
- 修改地图、怪物、战斗、美术或数值；
- 从原 0.0.9 迁移任何功能成果；
- 提前执行 `P1.0.r0` 或后续任务。

若为了使 0.0.8 镜像在新的 0.0.9B 根目录中正常识别、生成工程文件、编译或启动，需要进行路径、项目标识、文档或等价的非功能性适配，可以在最小范围内处理，并在 Report 中逐项记录。若发现必须修改 Gameplay 权威或既有关键逻辑才能完成接收，应停止该修改并交回策划判断。

# 下半部分：授权执行内容

## 5. 总目标

建立或确认一个来源清楚、与原 0.0.9 隔离、能够正常构建和运行的 `Dev.D.UE.0.0.9B` 独立开发基线，并形成足够精确的现场系统盘点，使下一份 `P1.0.r0` 能基于真实工程而不是仅凭技术分析报告签发。

## 6. 执行内容

### 6.1 核对项目信息与交接材料

优先读取当前工程内能够确认 0.0.8 完成态和迁移关系的权威材料，包括但不限于：

- 0.0.8 Codex 版本技术交接报告；
- 0.0.8 Chat 版本策划报告；
- 当前项目的信息卡、`PROJECT.md` 或等价项目定位文件；
- 最新可运行入口、构建记录和必要测试结果；
- 0.0.9B 已存在时，其根目录内的来源说明和现状记录。

如部分材料不存在，不需要自行补写历史结论；在 Report 中明确列出缺失项，并以真实工程审计结果继续完成可完成部分。

### 6.2 建立或确认 0.0.9B 独立基线

1. 核实 0.0.8 稳定镜像的真实位置与完成状态。
2. 核实 0.0.9B 活动根目录是否已经存在。
3. 若不存在，基于 0.0.8 稳定镜像建立 0.0.9B 独立开发目录；保留源码、配置、内容、项目文件和继续开发所需工具，不必复制可重建缓存和无价值临时输出。
4. 若已经存在，先检查其来源与当前内容，不得覆盖、清空或重建未知工作。
5. 保持 0.0.8 冻结源不被修改。
6. 记录源目录、目标目录、复制或既有基线的时间与可验证依据。

### 6.3 原 0.0.9 隔离检查

确认 0.0.9B 没有把原 0.0.9 作为直接开发源，也没有在未授权情况下合并其新增实现。

检查应以来源记录、目录关系、关键文件差异和现有工程事实为依据。无需为了证明隔离而对大型二进制资产做无差别逐字节审计；应优先检查与原 0.0.9 新增方向有关的源码、配置、蓝图、UI、数据、测试和临时工具。

若发现疑似污染：

- 不要直接删除；
- 记录文件或资产、可能来源、影响范围和判断依据；
- 将最终状态标记为需要策划判断，等待后续任务处理。

### 6.4 构建与运行接收验证

在不新增 0.0.9B 功能的前提下，完成适合当前工程的最小有效接收验证：

- `.uproject`、Engine Association 和必要模块可识别；
- 项目文件可生成或现有工程可直接使用；
- 至少完成一次能够覆盖当前 C++/Blueprint 基线的构建；
- 使用当前权威入口完成一次基础启动或 Smoke；
- 核对玩家能够进入 0.0.8 的既有可运行流程，未出现由镜像接收造成的新阻断。

本任务不要求为了形式重复全部 0.0.8 终版验证。若完整 Cook/Package 成本明显高于接收收益，可以采用较轻的构建与运行证据，并在 Report 中说明选择。

### 6.5 相关系统现场盘点

盘点 0.0.8 中与 0.0.9B 直接相关的真实实现。至少覆盖：

- 物品定义与物品实例；
- 物品 ID、数量、等级、随机词条、价值等实例状态；
- 玩家背包、装备栏、空间道具和快捷栏；
- 宝箱、资源容器、尸体、地面掉落和拾取；
- 奖励生成与搜索读条／搜索揭示；
- 灵石或其他独立货币；
- Run 生命周期、撤离、死亡和放弃结算；
- 局外持久化、局内状态和 SaveGame；
- 当前 UMG 页面、输入模式、鼠标捕获和 UI 开关逻辑；
- 与上述系统相关的自动化、Smoke、调试命令和日志入口。

对每个领域尽量记录：

- 当前权威类、组件、Subsystem、结构体、蓝图或数据资产；
- 关键文件／资产路径；
- 真实数据存放位置；
- 主要调用入口与依赖；
- 当前 UI 是否直接改写数据；
- 是否存在重复权威或临时桥接；
- 对 0.0.9B 的建议：保留、扩展、适配、替换或待确认；
- 会影响下一任务拆分的技术风险。

盘点目标是让策划看懂真实边界，不要求在本任务中解决发现的问题。

### 6.6 项目定位文件

若 0.0.9B 尚无可用信息卡或项目定位文件，可建立或更新一份简短版本，至少记录：

- 项目编号与当前阶段；
- 活动根目录与 `.uproject`；
- UE 版本；
- 0.0.8 继承源；
- 原 0.0.9 不继承声明；
- Prompt、Task Report 和 Version Report 目录；
- 当前可运行入口；
- 当前任务和下一步状态。

不要在定位文件中复制整份版本历史或技术分析报告。
