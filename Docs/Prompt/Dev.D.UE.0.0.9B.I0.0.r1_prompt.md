# 上半部分：只读验收结论与版本边界

## 1. `I0.0.r0` 验收结论

`Dev.D.UE.0.0.9B.I0.0.r0_report.md` 可以作为现场调查记录保留，但其任务结果不予验收，不能据此进入 `P1.0.r0`。

原因不是构建或 Smoke 失败，而是基线来源违反版本的核心决定：

- Prompt 要求 0.0.9B 从 `Dev.D.UE.0.0.8` 稳定镜像重新开始；
- Prompt 明确禁止把原 `Dev.D.UE.0.0.9` 的代码、UI、数据、测试、临时修复或未完成系统自动并入 0.0.9B；
- `I0.0.r0` 实际把 `C:\AIDev\shanmen-ue\Dev.D.UE.0.0.9-XFix1` 复制为 0.0.9B；
- Report 自身确认当前盘点到的丰富物品、仓库、搜索、装备与 UI 能力属于原 0.0.9-XFix1 方向。

因此，`I0.0.r0` 所写的 `READY_FOR_P1_PLANNING_WITH_NONBLOCKING_FINDINGS` 不成立。该问题属于基线阻断，不得用“现有工程可构建”“现有游戏可运行”或“用户要求从现有游戏开始”解释为对原 0.0.9 继承禁令的撤销。除非策划后续针对具体成果逐项授权，原 0.0.9 只能作为隔离的只读历史参考。

## 2. 0.0.9B 不变的版本定位

0.0.9B 是原 0.0.9 基本放弃后的第二次开发方向，只继承 0.0.8 稳定完成态。

本版本目标仍是建立《山门》自己的类塔科夫物品管理框架：

> 备战整理 → 进入地图 → 搜索容器与尸体 → 转移、装备和管理物品 → 撤离 → 同一批真实战利品进入局外仓库。

本返工仍属于 I 阶段，只负责恢复来源正确、隔离成立、可构建、可启动且可供下一步规划的开发基线。不得借返工实现任何新的仓库、背包、搜索、装备、拖拽、物品详情、地图、怪物、奖励或结算功能。

## 3. 当前 0.0.9B 目录的性质

当前 `C:\AIDev\shanmen-ue\Dev.D.UE.0.0.9B` 是由 `Dev.D.UE.0.0.9-XFix1` 建立的临时副本，不是已验收的 0.0.9B 开发基线。

必须将其视为“来源不合格的待隔离现场”：

- 不得在其中继续 P 阶段开发；
- 不得把其中的系统盘点直接当作 0.0.8 现场事实；
- 不得删除、覆盖或静默清空；
- 可以读取并记录，用于证明来源和防止误混入；
- 只有在确认不存在 `I0.0.r0` 之后的未知人工或并行改动时，才可用非破坏性方式移动或改名为隔离副本。

# 下半部分：授权执行内容

## 4. 总目标

纠正 `I0.0.r0` 的基线来源错误：定位并验证真正的 0.0.8 稳定开发镜像，安全隔离当前由 0.0.9-XFix1 产生的临时目录，在预期活动根目录建立来源合格的 0.0.9B 独立副本，重新完成最小构建、启动 Smoke 与相关系统盘点。

若无法找到或唯一确认可继续开发的 0.0.8 源工程，本任务应以阻断报告结束，不得再次使用原 0.0.9、打包程序、反编译产物或人工拼接工程代替。

## 5. 执行步骤

### 5.1 冻结并核对当前错误基线

1. 停止在当前 0.0.9B 根目录中的任何功能开发。
2. 核对 `I0.0.r0` Report 之后是否存在未报告的新文件、源码修改、资产修改或并行任务输出。
3. 记录当前目录的来源说明、关键文件时间、源码与内容文件数量、关键 SHA-256、构建输出状态和最后修改时间。
4. 如果确认当前目录只包含 `I0.0.r0` 迁移内容及其构建／Smoke 生成物，可将整个目录非破坏性改名或移动为清楚标记的隔离副本，例如：

   `C:\AIDev\shanmen-ue\Dev.D.UE.0.0.9B_QUARANTINE_I0R0_FROM_0.0.9-XFix1_<timestamp>`

5. 隔离操作不得删除任何源码、资产、文档或报告；必须记录隔离后的准确路径。
6. 如果发现 `I0.0.r0` 之后存在来源不明或尚未交接的工作，不要移动、覆盖或清理，直接转入 `NEEDS_PLANNER_DECISION`，列出冲突项。

### 5.2 定位真正的 0.0.8 稳定开发镜像

进行有边界的只读查找，优先覆盖项目相关位置和现有信息卡／交接报告实际引用的位置，包括：

- `C:\AIDev\shanmen-ue\` 下的 `Dev.D.UE.0.0.8`、`Dev.D.UE.0.0.8-XFix*`、冻结目录和相邻版本目录；
- 项目已登记的归档根目录；
- 项目相关的 `Docs\Report`、`Docs\Prompt`、Version Report、Chat Report、项目卡、`PROJECT.md`、`CODEX_PROJECT_HANDOFF.md`、`LATEST_BUILD.txt` 和运行入口；
- 与 0.0.8 终版或人工验收通过明确对应的冻结源工程。

对每个候选源记录：

- 完整路径和 `.uproject`；
- 项目编号、版本标记与 UE 版本；
- 是否包含可继续开发的 `Source`、`Content`、`Config` 和项目文件；
- 对应 Codex／Chat 版本报告、F2 迁移记录或人工验收记录；
- 关键文件时间、数量和抽样 SHA-256；
- 构建／运行入口；
- 与 0.0.9-XFix1 的关系；
- 能否被唯一判断为 0.0.8 稳定完成态。

证据优先级建议为：0.0.8 的 F2／版本交接记录与终版验收记录，其次是项目定位文件和冻结目录说明，再其次是目录命名、时间和文件差异。目录名称相似本身不足以证明来源。

`Latest_Demo`、已 Cook／Package 的 Windows 程序或仅含二进制的归档可以作为运行验收证据，但不能代替可继续开发的 0.0.8 源工程。

### 5.3 来源裁决

仅在以下条件同时满足时，才可选择某一候选作为继承源：

1. 它能由交接／验收证据明确对应到 0.0.8 稳定完成态；
2. 它是完整且可继续开发的 UE 源工程；
3. 它不是原 0.0.9、0.0.9-XFix1 或由其反向复制／删改伪装的目录；
4. 不需要推测性拼接多个版本才能成立；
5. 该冻结源可以保持只读，不在本任务中被修改。

若不存在满足条件的候选，或多个候选之间无法唯一裁决：

- 不得自行选择“最接近”的版本；
- 不得继续使用当前 0.0.9B 临时目录；
- 不得从 0.0.9-XFix1 删除若干文件后冒充 0.0.8；
- 不得从打包程序反向恢复工程；
- 不得创建空白 UE 项目代替；
- 生成 `BLOCKED` 或 `NEEDS_PLANNER_DECISION` Report，写明已查位置、候选差异、缺失证据和需要用户／策划提供的最小材料。

### 5.4 建立干净的 0.0.9B 基线

只有来源裁决通过后才执行本节。

1. 确认原 0.0.8 冻结源未被修改。
2. 在准确的 `C:\AIDev\shanmen-ue\Dev.D.UE.0.0.9B` 建立独立副本。
3. 复制继续开发所需的源码、配置、内容、项目文件、构建脚本和必要文档。
4. 不复制可重建缓存、旧构建输出、无价值临时目录或旧版本 Report 集合；具体排除项按真实工程判断并记录。
5. 仅允许为新根目录识别、工程生成、构建和启动进行最小非功能性适配。
6. 不得从隔离的 0.0.9／0.0.9-XFix1／错误 0.0.9B 目录迁入任何 Gameplay、UI、数据、资产、测试或临时修复成果。
7. 对新 0.0.9B 与选定 0.0.8 源进行结构／抽样哈希核对，并对原 0.0.9 新增方向的关键源码、UI、资产和测试做有针对性的污染检查。
8. 创建或修正 `PROJECT_INFO_CARD.md`、`PROJECT.md` 或等价定位文件，准确写明 0.0.8 继承源、原 0.0.9 不继承、当前阶段和文档目录。
9. 归档本 Prompt，但不得把 `I0.0.r0` 的错误系统盘点复制为当前 0.0.8 事实。

### 5.5 构建与运行接收验证

在不新增功能的前提下完成：

- `.uproject`、Engine Association 和模块识别；
- 至少一次覆盖当前基线的 Editor／Game Development 构建，或等价且理由充分的构建组合；
- 使用 0.0.8 权威入口或等价 Editor `-game` 入口完成基础 Smoke；
- 验证默认地图可以加载、进程正常退出、无本次迁移引入的 Fatal／阻断错误；
- 记录命令、退出码、关键日志和产物路径。

本任务不要求重新制作 `Latest_Demo`，也不要求执行版本末人工试玩。

### 5.6 基于真实 0.0.8 的系统盘点

若建立了合格基线，重新盘点与 0.0.9B 直接相关的真实 0.0.8 实现，至少覆盖：

- 玩家背包、装备栏、空间道具、固定6格和1—9快捷栏；
- 宝箱、资源容器、尸体、地面掉落、奖励生成与搜索状态；
- 灵石等独立货币；
- Run、撤离、死亡、放弃、结算与持久化；
- UMG 页面、输入模式、鼠标捕获和 UI 开关；
- 相关自动化、Smoke、日志和调试入口。

对每个领域说明真实权威、文件／资产路径、现有能力、重复权威或临时桥接、对 0.0.9B 的保留／扩展／替换建议和下一任务风险。
